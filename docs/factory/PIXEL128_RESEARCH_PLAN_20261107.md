# Pixel128 연구 계획, 2026-11-07

**상태:** PLAN_ONLY / GENERATION_NOT_RUN / 재개 승인 대기. 이 문서는 생성·설치·모델 변경을 하지 않았다.
AGENTS.md가 다시 연 픽셀 범위는 Pixel64뿐이다. 이 계획의 실행은 사용자가 128px 연구를 명시적으로
재개한 뒤에만 시작한다.

## 범위 결정 (2026-11-07 사용자 답변)

일반 필드 캐릭터는 64px로 충분하다고 판단했다. 기존 64px 후보 9장을 640×360 화면에 원래 크기로
놓으면 캐릭터 높이는 51~62px, 화면 높이의 약 1/6이고, 실루엣·장비·직업이 읽힌다. 한계는 얼굴이다.
머리 폭이 12~14px, 눈이 1~2px라 미묘한 표정은 담기지 않는다.
(근거 이미지: `workspace/pixel128-scope-20261107/`, git 제외)

128px 용도는 둘이다.

| 용도 | 화면에서의 위치 | 핵심 요구 |
| --- | --- | --- |
| 보스·대형 몬스터 | 64px 캐릭터와 같은 화면, 같은 픽셀 크기 | 프레임 애니메이션, 64px 캐릭터와 팔레트·외곽선 규칙 일치 |
| 대화 초상화·표정 | 대화창 UI | 같은 인물의 표정 변형, 64px 필드 캐릭터와의 동일성 |

두 용도 모두 프레임 애니메이션이 필요하다(초상화는 표정 전환·말하기 프레임 수준).
128px 일반 캐릭터는 범위가 아니다.

**기준 해상도는 미정이다.** 평가는 640×360(720p ×2, 1080p ×3 정수 확대)을 가정한다.
이 가정에서 128px 보스는 화면 높이의 약 1/3이다. 초상화는 UI라 기준 해상도와 따로 평가한다.
해상도가 정해지면 이 가정을 바꾼다.

| 항목 | 상태 | 근거 |

핵심 질문은 해상도보다 **픽셀 덩어리 정돈**이다. 1024px에서 128px는 8배 축소라
일러스트의 그라데이션과 잔디테일이 남기 쉽다. 예전 불합격이 이 경우였다.

## 공통 규칙

Pixel64 계획의 공통 규칙을 그대로 따른다. 실행마다 따로 예약하고 1회만 시도하며, 재시도와
대체 경로를 쓰지 않는다. 실패한 게이트를 넘어가지 않는다. 모든 출력은 REVIEW_REQUIRED이고,
Aseprite 사람 승인 전에는 Static Master가 아니다. MCP 도구는 6개를 유지하고, 실행 산출물은
`workspace/`에만 둔다. 경로 선택은 채택된 스프라이트(또는 애니메이션) 한 개당 총시간으로 하고,
사람 수정 시간(분)은 사용자가 직접 입력한다.

## 실험 순서

### E0. 오프라인 지표 (생성 0)

기계 지표는 사람 검토를 대신하지 않는다. 검토자에게 의심 지점을 알려 주는 참고 지표다.

- **유효 해상도:** 2×2 블록 균일도. 128px 결과가 64px를 2배로 늘린 것과 같은지(가짜 128) 잡는다.
- **덩어리 정돈도:** 고립 픽셀 비율(같은 색 이웃이 없는 픽셀), 색별 평균 클러스터 크기.
- **축소 가독성:** 64px·32px로 줄였을 때의 실루엣. 보스는 64px 캐릭터 옆에 놓은 장면 미리보기.
- **색 수:** 선언 팔레트 준수. 128px 색 상한은 E1 결과를 보고 사용자가 정한다.

보정: Pixel64 후보 9장을 2배로 늘린 이미지는 유효 해상도 지표에 걸려야 한다. `sword_warrior`
파일을 찾으면 음성 기준 샘플로 쓴다. 못 찾으면 NOT_FOUND로 기록하고 보정 없이 진행하지 않는다.

수용 기준: 지표 구현과 테스트, 보정 결과 기록.

### E1. 보존 원본 재정제 (생성 0, Refiner만)

1024px 원본 9장에 Refiner를 128×128로 한 번씩 돌린다. 설정은 사전에 선언한다.
`k2-pixel64` 격자에 128px 정보가 있는지, 아니면 가짜 128인지 E0 지표와 사람 확인으로 판단한다.

- 가짜 128이면 이 경로는 128px 생성에 쓰지 않고 E2·E5로 간다.
- 진짜 128이지만 덩어리가 어지러우면 E2(구조 고정)를 우선한다.

### E2. 계층형 64→128 (보스 정지 이미지)

사람이 승인한 64px를 실루엣·팔레트 기준으로 고정하고 128px로 디테일을 올린다.
게이트: 128px를 64px로 줄였을 때 기준 64px와 실루엣이 일치하고, 팔레트 밖 색이 0이어야 한다.
방법(저노이즈 img2img + Refiner, 수작업 보조 등)은 실행 전에 하나를 선언한다.
이 실험이 예전 불합격 사유를 구조적으로 피하는 길이라 가장 유망하다고 본다(가설).

### E3. 초상화와 표정 변형

128px 흉상 한 장을 기준으로 표정 변형을 만든다. 얼굴 영역만 바꾸는 `pixel-edit` 방식의 마스크 편집을
128px로 넓히는 것이 기본안이다. 게이트: 마스크 밖 변경 0, 팔레트 준수. 동일성은 사람 검토다.
64px 필드 캐릭터와 같은 인물로 보이는지도 사람 검토 항목이다.

### E4. 128px 프레임 애니메이션 안정성

보스 한 마리의 짧은 루프(대기 4~6프레임) 하나로 방법을 비교한다. 후보:
(a) NONPIXEL 모션 잡 프레임을 프레임마다 같은 팔레트·격자로 픽셀화,
(b) 부위 분리(컷아웃) 애니메이션, (c) 사람 키프레임 + 보조 생성.
지표: 프레임 간 팔레트 동일, 정지해야 할 영역의 깜박임 픽셀 수, 기준선·앵커 고정.
애니메이션 실행에는 승인된 Static Master가 필요하다.

### E5. 픽셀 전용 생성기 (Pixel64 P4와 통합)

128px를 직접 지원하는 생성기 한 곳을 같은 Brief·게이트·장부로 비교한다. 후보는 사용자가 고르고,
유료라면 예산 승인을 먼저 받는다.

## 필요한 코드 변경 (재개 후)

- `pixel-ledger`의 64×64 고정을 선언한 논리 크기(64 또는 128)로 넓힌다.
- `pixel-transparent`, `pixel-edit`의 64px 전제를 같은 방식으로 넓힌다.
- E0 지표 모듈과 테스트.

## 하지 않는 것

32px, 128px 일반 캐릭터, 128px 전용 LoRA 탐색·학습(E1 결과로 필요성이 확인되면 따로 요청),
자동 provider 선택, 자동 재시도, 사람 승인 대행, Golden/SOT 변경, MCP 도구 추가.
